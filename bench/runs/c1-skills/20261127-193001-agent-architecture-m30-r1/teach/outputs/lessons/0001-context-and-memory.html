Context and memory: what your agent can actually see

By the end of this lesson you can decide, for any piece of information in your makerspace assistant, whether it goes in the context, gets saved for later, or gets looked up when needed, and you can defend that choice with a token count.

Objective O3: context and memory in an agent About 30 minutes Cheat sheet: context and memory
Why this matters for you

Your assistant has to answer from long machine manuals, remember students between visits, and stay inside a small model budget. All three come down to one design question: what text does the model receive on each call? At your design review, that is the question to have an answer for.

Warm-up 2 min

Recall from earlier

A chatbot confidently gives last year's makerspace opening hours. You paste this year's hours into your message and ask again, and now it gets them right. Using what you know about language models, explain both answers. Where can the model's information come from?

A model has two sources: patterns learned in training, and the text it is given right now. The first answer came from training, which stops at some date, so it produced plausible but stale hours. The second time, the correct hours were in the input. Nothing was retrained. Today's lesson is about controlling that second source.

1. The context window 4 min

Goal: know what the model sees on one call, how big it can be, and what it costs.

Models read text in tokens: small chunks that may be whole words, parts of words, or single characters. One provider's glossary puts a token at roughly 3.5 English characters on its newer models. The ratio differs between models, so treat any rule of thumb as an estimate and use a token counter when the number matters.

The context window is all the text the model can reference while producing a response, including the response itself. The documentation calls it the model's "working memory," and it is separate from what the model learned in training. It has a maximum size, counted in tokens.

Analogy: think of RAM, not the hard drive. A program can only work on what is loaded. The manual sitting on your disk might as well not exist until some of it is loaded in.

What takes up space

Everything in the request counts, and so does the output:

  • System prompt: the standing instructions your program sends ("You are the makerspace assistant...").
  • Tool definitions: each tool's name, description and parameters.
  • Messages: what the student typed and what the model replied.
  • Tool requests and results: calendar entries, manual text, training records.
  • The new output: the tokens the model is writing now.

Why "it fits" is not good enough

  • Hard limit: if the input alone is bigger than the window, the API in those docs rejects the request with an error. A response that runs into the limit partway gets cut off.
  • Quality: as the context grows, the model's ability to recall details from it tends to drop. This is called context rot. Anthropic's engineers describe it as a gradual slope rather than a cliff.
  • Cost: model APIs commonly charge per token, so every token you send is paid for, on every call that includes it. (Some offer a discount, called caching, for repeated text. It lowers the price, but the text still fills the window.)

The design aim, in the words of that engineering article, is "the smallest possible set of high-signal tokens that maximize the likelihood of some desired outcome." In game terms: an inventory with limited slots. Carrying everything slows you down and buries the item you need.

Check yourself

Your team adds twelve new tools with long descriptions. A student asks a question that needs none of them. What happens to that request?

2. Between steps: the program keeps the history 5 min

Goal: understand how an agent "remembers" what it did two steps ago.

The surprising part: the model keeps nothing between calls. A basic model API is stateless, meaning each request is handled on its own. One provider's documentation says it plainly: you "always send the full conversational history to the API." (Some APIs offer to store the history for you. The stored text still has to reach the model as context; only who holds it changes.)

So the memory inside a task is a plain list that your program owns. On each step of the loop:

  1. The program sends the whole list to the model.
  2. The model replies with a tool request or a final answer.
  3. The program appends that reply to the list.
  4. If it was a tool request, the program runs the tool and appends the result.
  5. Repeat.

Analogy: a brilliant consultant with total amnesia. Every time you phone, you read them the whole case file, they say what to do next, you do it, and you write the outcome in the file. The continuity is in the file.

Here is that idea in Python-style code. call_model and run_tool are placeholders; you don't need a real model to read it.

messages = [{"role": "user", "content": question}]

for step in range(MAX_STEPS):
    reply = call_model(SYSTEM, TOOLS, messages)  # sees only these
    messages.append(reply)

    if reply["type"] == "final_answer":
        break

    result = run_tool(reply["tool"], reply["args"])  # your code runs it
    messages.append({"role": "tool", "content": result})

Delete the last line and the model would ask for the same information again, because from its point of view nothing ever came back.

Worked example: counting the tokens

Worked example (made-up sizes and price)

System prompt plus tool definitions: 1,500 tokens. Question: 50. The model requests a calendar check (request 50, result 600), then a manual search (request 50, result 2,000), then answers. Price: $1 per million input tokens. Ignore output cost.

  1. Call 1 sends the base and question: 1,500 + 50 = 1,550.
  2. Call 2 adds step 1: 1,550 + 50 + 600 = 2,200.
  3. Call 3 adds step 2: 2,200 + 50 + 2,000 = 4,250.
  4. Total billed input is the sum of the calls, not the size of the last one: 1,550 + 2,200 + 4,250 = 8,000 tokens.
  5. Cost: 8,000 / 1,000,000 × $1 = $0.008 per question, or $8 per 1,000 questions.
Your turn

Base: 2,000 tokens. Question: 100. Three tool steps, then a final answer. Each request is 100 tokens; the results are 300, 1,400 and 900 tokens, in that order. (a) List the input size of every call. (b) Find the total input. (c) How much total input would you save if your program cut the 1,400-token result to 400 tokens before adding it to the list?

(a) Call 1: 2,100. Call 2: 2,100 + 400 = 2,500. Call 3: 2,500 + 1,500 = 4,000. Call 4: 4,000 + 1,000 = 5,000.

(b) 2,100 + 2,500 + 4,000 + 5,000 = 13,600.

(c) The 1,000 tokens you cut would have appeared in calls 3 and 4, so you save 2,000 (new total 11,600). If you said 1,000, you counted the result once. It is resent on every later call.

3. Keeping a long task from overflowing 3 min

Goal: shrink the list without losing what the task still needs.

A two-step booking question is harmless. A 40-step debugging session, or a student chatting for an hour, is not: the list keeps growing. Your program can edit it, because your program owns it.

TechniqueWhat the program doesRisk
Trim results at the sourceTools return only the useful fields (Friday's free slots, not the whole month).Leaving out a field that turns out to matter.
Clear old tool resultsReplaces raw output from long ago with a short placeholder.The model may need to call the tool again.
CompactionSummarizes the history and starts a fresh context from the summary.A detail missing from the summary is gone from the model's view.

Anthropic's article calls clearing old tool results one of the lightest-touch forms of compaction. For compaction summaries, it advises first making sure everything important is captured, and only then cutting the fluff. Its coding-agent example keeps decisions and unresolved bugs and drops redundant tool output.

Analogy: a game's save file stores your inventory, quest state and position. It does not store every button you pressed to get there. A good summary is a good save file.

Think it through

A student has spent 30 messages planning a laser-cut enclosure with your assistant, and the context is nearly full. Name two facts the summary must keep and one thing it can safely drop. Say why.

Keep things later steps depend on and that cannot be cheaply recovered: the decisions made (material, thickness, dimensions), constraints the student stated (deadline, budget), what is booked or still pending. Drop things that are finished or can be fetched again: raw calendar listings already used, manual passages that were read and acted on, greetings. Test each item with: "If this vanished, would the next answer be wrong?"

4. Between sessions: memory is something you build 4 min

Goal: decide what survives after a student closes the chat.

When a session ends, the message list is only still there if your program saved it. And even a saved list does nothing until the program puts some of it back into a later request. Two terms, as used in one agent framework's memory guide:

  • Short-term memory: the history of one conversation (the list from section 2).
  • Long-term memory: information stored outside the conversation and available across sessions.
A common mix-up

"The agent will remember this from last time on its own." It is tempting because some chat products appear to remember you, and because within one conversation the model does seem to recall everything. In both cases, software around the model is storing text and sending it back in. A model call does not update the model. If Maya says on Monday "I use PLA filament" and your program stores nothing, then on Thursday the model has no trace of it, not even a vague one. To get memory you must write three things: what to save, where, and when to load it.

What deserves saving?

The same memory guide sorts long-term memory into three kinds. Here they are in makerspace terms:

KindMeaningYour assistant
SemanticFacts"Maya prefers PLA."
EpisodicPast events"Last visit, Maya's print failed from poor bed adhesion."
ProceduralHow to act"Check training before booking." (usually in your prompt or code)

My design advice for your review, beyond what the sources say:

  • Official records stay in their own system. Training status and bookings have a source of truth. Look them up with a tool each time. A copy in a memory note goes stale the day a certification expires.
  • Save what is useful later and not recorded elsewhere: preferences, an unfinished project, a recurring problem.
  • Date every note, and let it be corrected or deleted.
  • Load only this student's relevant notes. It protects privacy and keeps the context small. Your code should enforce whose notes get loaded.

When to write? During the conversation, a memory is available immediately but the extra work adds delay. In a background job afterward, the reply stays fast, but you must decide when the job runs, and a later session may miss recent facts (the guide's trade-off).

5. Retrieval: finding the right manual page 5 min

Goal: answer from a long manual without sending all of it.

Suppose a manual is 200 pages at about 500 tokens each (an assumption): 100,000 tokens. At our made-up $1 per million, including it costs $0.10 per call, so a three-call question costs about $0.30, before any caching discount. Sending five passages of 400 tokens costs 2,000 tokens per call.

Retrieval means searching a store for the relevant pieces and placing only those in the context. Using it to ground a model's answer is often called retrieval augmented generation (RAG). Think of an open-book exam: you use the index, open two pages, and answer from them.

The usual pipeline

  1. Chunk (once, in advance): split each manual into passages, typically no more than a few hundred tokens.
  2. Index (once): store the chunks so they can be searched.
  3. Search (per question): find the best few matches, called the top-k (k is how many you keep).
  4. Insert: put those chunks in the context, with machine name and page number, and ask the model to answer from them.

Two ways to search

  • Keyword search matches words and phrases (a common scoring method is called BM25). Good for exact strings like an error code "E-42".
  • Embedding search turns text into lists of numbers so that passages with similar meaning sit close together. It can match "the plastic won't stick" to a section on bed adhesion.
  • Hybrid runs both and merges the results, since each catches things the other misses.

Where it breaks

  • Wrong chunk, confident answer. The model answers from what it got. If search returns the wrong machine's page, the reply can sound just as sure.
  • Lost context. A chunk reading "Do not exceed 60% power" is useless if the heading naming the machine and material was cut off. Keep that information attached to each chunk. The contextual retrieval article shows that adding a short description to each chunk before indexing reduced search failures in its tests.

When to fetch, and whether you need this at all

  • Up front: your program searches before the first model call. Predictable and fast.
  • Just in time: the model gets a tool such as search_manuals(query) and calls it when needed, possibly again with better words. More flexible, but slower, and a poorly guided agent can waste context on dead ends.
  • No retrieval: if all your documents are small, include them whole. The same article suggests this below about 200,000 tokens, with caching, on the models it discusses. "Fits" still has to pass your budget and quality tests.

A student types: "My cutter shows error LC-207." The right page contains that exact code. Searches using only meaning-based matching keep returning general troubleshooting pages. What is the best fix?

6. Notes as memory 2 min

Goal: let the agent keep its own place in a long job.

Structured note-taking means the agent regularly writes notes to storage outside the context window and pulls them back in later. A to-do list or a NOTES.md file counts. You offer tools such as write_note and read_notes; the model decides what to write, and your program does the saving.

Analogy: the quest journal in an RPG. You can stop for a week, open the journal, and know what to do next.

# Project: Maya's enclosure   (updated 2026-11-27)
Decided: 3 mm plywood, box 120 x 80 x 40 mm
Done: laser training verified in records
Open: test cut not yet run
Next: book a 1-hour slot once Maya picks a day

How the three tools of this lesson differ:

  • Compaction condenses the history when it gets long.
  • Notes record chosen facts as the work goes, and survive a context reset.
  • Retrieval finds pieces in a store, whether manuals or a large pile of notes.

Notes are only as good as what got written. A wrong note will be read back and believed, so keep notes short, dated and checkable.

Think it through

A note says "Maya's slot is booked," but the booking tool actually returned an error. What goes wrong later, and what rule would prevent it?

A later session reads the note, treats the booking as real, and may tell Maya to show up. Prevent it by recording only confirmed outcomes (ideally written by code from the tool's result, with a booking ID), and by checking the calendar again before relying on a booking.

Worked example and practice 4 min

Use four questions on each piece of information: Is it needed on this call? Does it change? Is it large? Is it needed after the session?

Worked example

Maya asks: "Can I cut 3 mm acrylic on the laser cutter Friday, and what settings do I use?" Plan the memory.

  1. Assistant rules and tool definitions: needed on every call, small, stable. Always in context.
  2. The question and this chat: needed now. Message list, kept by the program.
  3. Friday's availability: changes often. Look up with the calendar tool, return only Friday, never save as a memory.
  4. Her training status: official and can expire. Query the records system.
  5. Acrylic settings: buried in a long manual. Retrieve the matching chunks, labeled with machine and page.
  6. "Maya is building a lamp": useful next visit, recorded nowhere else. Save a dated note, load it next time.
Your turn

Sam says: "My 3D print keeps warping, same as last week. Can you check what we tried and book the printer for Tuesday?" Sort each item into: always in context, message list, live lookup, retrieval, or long-term note. Give a reason for each, and say what should be saved at the end. First item done: tool definitions: always in context, since every call needs them. Now do: Sam's current message; what was tried last week; the printer manual's warping advice; Tuesday's availability; Sam's training status.

  • Current message: message list; the task is built on it.
  • Last week's attempts: long-term note, loaded for Sam. It exists only if last week's session saved it. If it did not, the assistant should say it has no record and ask.
  • Warping advice: retrieval from that printer's manual; large and mostly irrelevant otherwise.
  • Tuesday's availability: live calendar lookup; it changes.
  • Training status: live records lookup; official and can expire.
  • Save: a dated note with today's symptom and what was suggested, marked untested until Sam reports back. The booking itself lives in the calendar.

Grade yourself hard: did you say what happens if the old note does not exist?

Hands-on build after the lesson

No model or API needed. In plain Python:

  1. Save a few notes per student in memory.json.
  2. Write load_notes(student) and save_note(student, text), adding a date.
  3. Write search(chunks, query, k) that scores each manual chunk by shared words and returns the top k.
  4. Write build_context(student, query) that joins a system prompt, that student's notes and the top chunks.
  5. Print an estimated token count (characters ÷ 3.5, a rough guess).

Pass test: run it, quit Python, run it again: saved notes still appear, and Maya's context never contains Sam's. Then try a query that uses different words from the manual and watch your keyword search miss.

Summary 1 min

  • The context window is everything the model can reference on a call, including its output. It is limited, billed, and gets less reliable as it fills.
  • Between steps, your program keeps the message list and resends it. Trim, clear or compact it when it grows.
  • Between sessions, only what your program saves and reloads is remembered.
  • Retrieval brings in the few relevant chunks; notes let an agent record its progress outside the window.
  • Changing official facts get looked up live.

Say it in your own words: a teammate says, "We don't need to design memory; the AI will just remember students." Correct them in three sentences, without looking.

Explain it

Check that yours says: (1) a model call retains nothing for the next one; (2) our program must save information in storage; (3) it must load the relevant part back into the context, which costs tokens, so we choose what to load.
