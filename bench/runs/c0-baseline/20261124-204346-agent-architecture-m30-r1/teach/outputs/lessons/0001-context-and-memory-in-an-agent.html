Context and memory in an agent

By the end of this lesson you can decide, for the makerspace assistant, what goes into the model's context on each call, what is saved between sessions, and how it finds the right page in a long manual.

Objective O3: context and memory in an agent About 30 minutes Builds on your work on the agent loop (quiz 0001)
Why this matters for you

Your assistant must answer from long machine manuals and remember each student's training status between visits, on a small budget. Both problems are context and memory problems, and the choices you make here decide what each request costs. You will be able to defend those choices at your design review.

The context window 6 min

Start with a concrete case. A student types: "How do I change the blade on the band saw?" Your program sends the model a block of text made of the instructions you wrote for it, the descriptions of its tools, and the question. The model reads that text and writes a reply. That block of text is the model's whole world for that call.

The context window is all the text a language model can reference when it generates a response, including the response itself. The Claude documentation calls it the model's "working memory", and says it is different from the large body of text the model was trained on (Claude docs: Context windows). Training taught the model language and general knowledge. It did not teach it your makerspace's manuals, and it does not teach it anything about this student.

The window is measured in tokens: the small pieces of text, often a word or part of a word, that the model reads and writes. A page of a manual is roughly several hundred tokens. Every model has a maximum number of tokens it can take in one call. Beyond that limit, there is no room.

Everything the model needs must be inside the window, because nothing else exists for it. The docs list what counts toward it: the system prompt, all the messages including tool results, the tool definitions, and the model's own output (Claude docs). The system prompt is the standing instructions you write, such as "You are the makerspace assistant. Never book a machine for a student without a training record."

A common mix-up

"A bigger window means I can put everything in and stop worrying." It is tempting because current models accept very large windows; the Claude docs list windows up to 1 million tokens for some models. But Anthropic's engineers describe context as "a finite resource with diminishing marginal returns": as the number of tokens grows, the model's ability to recall details from them gets worse, a problem called context rot (Anthropic: Effective context engineering for AI agents). Length also costs money, as the next section shows. The goal is the smallest set of useful tokens, not the largest set that fits.

What is kept between steps 6 min

Here is the surprise that surprises most people. The model does not remember the previous step. Each call to the model starts fresh. What looks like memory inside a conversation is your program sending the whole history again: the Claude docs say each turn's input is all the previous conversation history plus the new message (Claude docs). In an agent, "history" includes every tool request and every tool result so far.

That is why Figure 1 grows downward. At the third call of the laser cutter question, the model sees the question, its own first tool request, the calendar result and its second request, because your program put them there.

This matters for your budget, because model usage is billed per token, and on every call you pay for all of the input again. Here is a small worked example. The numbers are made up to show the pattern, not measured from a real model.

Worked example: counting input tokens

The system prompt and tool descriptions take 2,000 tokens. The question takes 50. Each tool request takes about 50 tokens and each tool result 400. The model makes three tool requests and then writes its answer, which is four calls.

  1. Call 1 input: 2,000 + 50 = 2,050 tokens.
  2. Call 2 input: call 1's input, plus the 50-token request and the 400-token result = 2,500.
  3. Call 3 input: 2,500 + 450 = 2,950.
  4. Call 4 input: 2,950 + 450 = 3,400.
  5. Total input paid for: 2,050 + 2,500 + 2,950 + 3,400 = 10,900 tokens, although the new information in the whole conversation is only about 1,400 tokens beyond the fixed 2,000.

Each call re-reads everything. A longer loop costs more than a proportional amount, because each additional step carries all the earlier steps with it. Two habits keep this in check: keep the fixed part (system prompt and tool descriptions) short and precise, and keep tool results small. Anthropic's guidance for agents is the same: aim for "the smallest possible set of high-signal tokens", and keep tool sets minimal and their outputs token-efficient (Anthropic).

When a loop runs so long that the window nears its limit, there are ways to shrink it. Compaction means summarizing the conversation so far and starting a fresh context with the summary. Clearing old tool results is described in the same post as one of the safest, lightest forms of compaction. You likely will not need either for short makerspace requests, but you should know they exist.

What is kept between sessions 4 min

Now back to your prediction. A session is one run of the assistant: from a student's first message until the conversation ends. When the session ends, the history your program was holding is gone, unless your program saved it somewhere. The model itself keeps nothing: it is not updated by your conversations, and nothing in it changes after a call.

So tomorrow, a new session starts with the system prompt, the tool descriptions and the student's new message, "Thanks, can you book it?" The model has no idea what "it" is. If your program does not carry anything over, it will ask, guess, or invent.

A common mix-up

"The assistant learns from its conversations and remembers each student." It is tempting because chatbots you have used seem to know you. When one does, a program around the model is storing something and putting it back into the context at the start of the next session. The model did not learn it. For your assistant, nothing is remembered unless you decide what to save, where to save it, and when to load it.

That is good news for design, because it makes memory a choice you control. Compare the two ends of what you could do:

OptionWhat it savesCost and risk
NothingNothing; each session starts blankCheapest; the student repeats themselves every visit
Store whole past conversations and reload themEverything the student saidEvery old token is paid for again; context rot; private details travel along
Store a few facts, load them at the start"Trained on laser cutter, 12 March"Small, cheap and checkable

Notes as memory 5 min

The simplest working memory for an agent is the one you use: write it down. Structured note-taking, which Anthropic also calls agentic memory, is when the agent writes notes to storage outside the context window and reads them back later. Anthropic gives the examples of an agent keeping a to-do list and an agent maintaining a NOTES.md file. In one example, an agent playing a game tracked its goals across thousands of steps, and after its context was reset it read its own notes and carried on (Anthropic).

For your assistant, a note is a small record per student, written by a tool and read by a tool. The model decides when to call them, just like check_calendar:

save_note(student_id, text)   # e.g. "Trained on laser cutter, 12 Mar. Prefers evenings."
read_notes(student_id)        # returns the saved notes for this student

Notes work well for small, durable facts: training status, preferences, a booking the student wants to make later. They work badly for large material, such as a whole manual, because the notes must also fit in the window when loaded. Also, a note is only as good as what the model chose to write, so decide the format in your tool description, for example "one short line per fact, with a date".

Retrieval as memory 6 min

Notes cover small facts. Your manuals are a different problem: a long document that most questions need only a tiny piece of. Suppose a laser cutter manual is 60,000 tokens. Putting it in the context for every question would, by the counting in the last section, mean paying for 60,000 tokens on every call of the loop. And the model would have to find one paragraph in it, which gets harder as the window fills.

Retrieval means fetching only the pieces of a document that match the question and placing just those in the context. The usual recipe, often called retrieval-augmented generation, has two stages:

  1. Prepare once, ahead of time. Split each manual into chunks (a section or a few paragraphs each) and build an index that can find chunks by meaning or by keywords. An embedding is a list of numbers that represents a chunk's meaning, so that chunks with similar meaning have similar numbers.
  2. Search at question time. Turn the question into the same kind of numbers, find the nearest chunks, and put the top few into the context. The model answers from them.

The original retrieval-augmented generation research paper describes exactly this combination of a model with a searchable index of outside documents (Lewis et al., 2020).

For an agent there is a second way to retrieve, and it fits the loop you already know. Instead of searching before the model starts, you give the model a search_manuals tool and let it decide when to look. Anthropic calls this "just in time" retrieval: the agent keeps lightweight pointers such as file names or stored queries and loads the data when it needs it. The same post notes the trade-off: it is slower than precomputed lookup, and it needs good guidance about when and how to search, or the agent wastes context. It also describes a hybrid, where a few things are loaded up front and the rest is fetched as needed (Anthropic).

A common mix-up

"Retrieval means the model has read the whole manual and looks things up in its head." It is tempting because the answers sound informed. In fact the model sees only the chunks your search returned. If the search returns the wrong chunk, the model answers from the wrong text, or fails to find the fact, however good the model is. Retrieval quality is a design problem for you: how you chunk the manuals, and how you describe the search tool.

Worked example and practice 8 min

Now put the pieces together on one request. Here is a design for the question "I trained on the band saw last month. Can I book it tomorrow at 2, and how do I change the blade?"

Worked example: deciding what goes where
  1. Start of the session, in context: the system prompt and the tool descriptions. They are the same for everyone and short. Keep them lean, because they are paid for on every call.
  2. Training status, from notes: the program (or the model, through read_notes) loads "Trained on band saw, September" into the context. It is a few tokens, and it answers whether the student may book.
  3. The booking, from a tool: check_calendar("band saw", "tomorrow 2 pm") returns "free". A one-line result, so it stays cheap in the history.
  4. The blade change, from retrieval: search_manuals("band saw change blade") returns the two best chunks, about 800 tokens. The model answers from them. The other 59,000 tokens of the manual never enter the context.
  5. Before the session ends: save_note stores "Asked about blade change, tomorrow 2 pm booking". The whole context is then discarded, and only the note survives.
Your turn

Use the same method for this request: "What are the laser cutter's settings for 3 mm acrylic? And remind me what I'm trained on."

Step 1 is given: the system prompt and tool descriptions are in the context on every call. Decide, for each of the three remaining items, whether it comes from notes, from retrieval, or from the context already in the window, and why: (a) the student's training status, (b) the acrylic settings, (c) the student's question itself. Then decide which of (a) and (b) you would keep out of the system prompt, and why.

Show a solution

(a) Training status comes from notes: it is a fact about this student, saved in an earlier session. (b) The acrylic settings come from retrieval: they are in the laser cutter manual, and only the matching chunk should be fetched. (c) The question is already in the context, since the program put it there when the student typed it. Both (a) and (b) stay out of the system prompt: (a) differs for every student, and (b) is a small part of a long manual that most questions do not need. Putting either in the system prompt would pay for those tokens on every call of every request.

Cost check

Using the numbers from the worked example in section 3 (fixed part 2,000 tokens, question 50), suppose each manual search returns 3,000 tokens and each tool request is 50 tokens. The model calls search_manuals once and then answers, so it is two calls. How many input tokens do you pay for in total? Then say how much of the total came from re-sending the search result.

Show a solution

Call 1: 2,000 + 50 = 2,050. Call 2: 2,050 + 50 + 3,000 = 5,100. Total: 2,050 + 5,100 = 7,150 tokens. The search result is in the input of call 2 only, because there is no call 3 to re-send it. In a longer loop, it would be paid for again on every later call, which is why result size matters more the longer the loop runs.

Summary 2 min

  • The context window is the model's working memory: only text inside it exists for the model on a call. It holds the system prompt, tool descriptions, messages and tool results.
  • Between steps, memory is the history your program re-sends, and you pay for it again on every call. Between sessions, nothing is kept unless you save it.
  • Notes store small facts outside the model and load them back; retrieval fetches only the matching chunks of long documents. Both are ways of choosing what enters the window.
  • The aim is the smallest set of useful tokens, for quality and for cost.
