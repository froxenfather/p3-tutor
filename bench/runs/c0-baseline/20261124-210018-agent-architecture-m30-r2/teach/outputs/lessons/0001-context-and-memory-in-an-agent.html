Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it lives in the context window, in saved notes, or in a manual that is searched on demand.

Objective O3: context window, what is kept between steps and sessions, retrieval and notes as memory About 30 minutes
Why this matters for you

Your assistant must answer from long machine manuals and remember each student's training status between visits, on a small budget. Those three jobs map onto three different kinds of memory, and the choice between them is exactly what you will defend at your design review.

The context window 5 min

Start with an everyday case. You hand a friend a single sheet of paper and say, "Answer the student using only this sheet." Whatever is on the sheet, they can use. Whatever is not on it, they cannot see. The sheet has a fixed size, and your friend reads all of it every time you ask.

A language model works like that friend. The context window is the model's sheet of paper: all the text it can see in one call, which is its instructions, the conversation so far, tool descriptions, tool results, and the answer it is writing. Its size is measured in tokens, small chunks of text, often a word or part of a word. The model's own reply counts toward the window too. Anthropic's documentation describes the window as the model's working memory for the conversation, and it notes that sizes differ by model, so check the current table before you plan around a number (Claude docs: Context windows).

Why the window affects cost and quality

Two facts matter for your budget. First, you pay for the tokens you send, and the whole window is sent on every call. Second, bigger is not simply better: Anthropic's docs warn that accuracy and recall can degrade as the token count grows. Anthropic's engineering team describes this as a limited attention budget, and says the goal is the smallest set of high-signal tokens that still gets the job done (Effective context engineering for AI agents). Long manuals pasted into every call are therefore both expensive and risky.

Rough scale for intuition: a token is a few characters, so a long machine manual can be tens of thousands of tokens. Your tokenizer or the API's token counter gives exact numbers; do not guess when you budget.

What is kept between steps 5 min

Back to your warm-up. Each step of the agent loop is a separate model call, and the model does not carry anything over from one call to the next. It keeps no hidden state between calls. So how does step 3 "remember" step 2?

It does not. Your program does the remembering. Before every call, the program builds the window again: it takes the stored list of messages (the question, each tool request, each tool result) and sends the whole list to the model. This stored list is the history, and it lives in your program, for example as a Python list of dicts.

history = [{"role": "user", "content": "Is the laser cutter free Friday?"}]
while True:
    reply = call_model(instructions, tools, history)   # the model sees all of history
    history.append(reply)                              # the program keeps it
    if reply is final_answer:
        break
    result = run_tool(reply)                           # the program runs the tool
    history.append(result)                             # next call will include it

This sketch is pseudocode, not a real library. What to notice is that history only grows within one run, and every call re-sends all of it. That is why long agent runs get steadily more expensive: step 10 pays again for steps 1 through 9.

A common mix-up

"The model remembers what happened earlier in the run." It is tempting because chatbots feel continuous. But what feels like memory is your program re-sending the history. If your program forgot to append a tool result, the model would simply not know it happened, and it might call the same tool again.

When the window fills up 4 min

A run with many tool results can outgrow the window, or just become expensive and less accurate before it does. Your program, not the model, decides what stays. Three common moves:

  • Clear old tool results. After the model has used a 20-page manual excerpt, the raw text rarely needs to stay. Anthropic calls removing stale content context editing (Managing context on the Claude Developer Platform).
  • Summarize. Replace the old part of the history with a short summary and continue from there. You lose detail, so keep what the task still needs: decisions made, open questions.
  • Keep results small in the first place. Return the three relevant paragraphs, not the whole manual. This is the cheapest of the three, and the next sections build on it.

Anthropic's guidance is to treat context as a limited resource and to include only high-signal information (Effective context engineering). For your assistant, that means a calendar tool should return the free slots for the asked day, not a month of bookings.

A common mix-up

"A bigger context window means I do not need retrieval or memory." It is tempting: why search at all if all the manuals fit? But you would pay for every manual token on every call, the model's accuracy can drop as the window fills, and the window still empties when the run ends. A big window postpones the problem; it does not remove it.

Between sessions: notes as memory 5 min

A session is one run of the assistant for one conversation. When it ends, your program's history is gone, and the next session starts with an empty window. The model has not learned anything: its training does not change when it is used. So if Sam finished laser-cutter training on Monday and returns on Thursday, the new session knows nothing, unless you saved it somewhere.

The simplest fix is notes: text the agent writes to storage outside the window, and reads back later. Anthropic's memory tool works this way. It lets Claude create, read, update and delete files in a memory directory that persists between sessions, and your application implements the storage side, so you choose where the files really live (Claude docs: Memory tool). The same idea works in any framework with two tools you write yourself.

save_note(student_id, text)   # e.g. "Completed laser cutter training 2026-11-17"
read_notes(student_id)        # returns that student's notes as text

At the start of a session the program (or the model, via read_notes) loads the student's notes into the window. During the session the model can add to them. Because the model chooses what to write, the descriptions you give these tools matter, as you saw with tool descriptions in the agent loop.

What belongs in notes

Keep as a noteDo not keep as a note
Facts that stay true and that you will need next time: training status, preferencesThe whole chat transcript: it is long, and mostly noise
Short, dated entries the agent can read in secondsFacts that change on their own, like the calendar. Look them up live instead
For training status you may not need the model to write notes at all. A plain database that your program reads at session start is more reliable than hoping the model saves the right fact. Notes written by the model are best for things only the model notices.
A common mix-up

"Telling the assistant something teaches the model." It feels that way, since it answers well afterward. In fact nothing is stored unless your program saves it. The model's training does not change during use, so Thursday's session knows Monday's training only if a note or record carries it over.

Retrieval: finding the right page 5 min

Notes are for small facts. Manuals are the opposite: large, fixed, and mostly irrelevant to any one question. The answer is retrieval: search a store of text outside the window, and put only the best matches into it. Think of a library. You do not carry the library into the exam room; you look up the book and bring one page.

How a manual gets searchable

  1. Chunk each manual into pieces of a few paragraphs, such as one section with its heading.
  2. Index the chunks so a search can rank them. Two common ways: keyword search (such as BM25, which scores chunks by matching words, so it is good for exact terms like a model number) and embedding search (each chunk becomes a list of numbers so that similar meanings are near each other, so "cutting thick wood" can match a section titled "Maximum material depth").
  3. Search when a question arrives, take the top few chunks, and return them as a tool result.

Anthropic's write-up on retrieval notes that chunks lose their surroundings: a chunk that says "the limit is 6 mm" does not say which machine. Their fix, contextual retrieval, prepends a short explanation of where each chunk comes from before indexing, and in their tests combining it with keyword search cut failed retrievals by 49% (Introducing Contextual Retrieval). A cheap version for you: start every chunk with the machine name and section heading.

Retrieval as a tool

In an agent, retrieval is just another tool, search_manuals(machine, query), and the model calls it when it needs it. Anthropic calls this just-in-time retrieval: the agent keeps light references and loads data when needed instead of pre-loading everything (Effective context engineering). Because the search ranks by similarity and not by truth, it can return a wrong or partial page. The model can then search again with different words, which is one reason retrieval fits an agent loop well.

A common mix-up

"Retrieval is the model remembering the manual." The model learns nothing from the manual. A search tool returned text and the program placed it in the window for this call. If the right chunk is not returned, the model cannot use it, so retrieval quality is a design decision, not a detail.

Worked example and practice 3 min

Worked example

Sam returns and asks, "Can I cut 5 mm acrylic on the laser cutter today at 2 pm?" Decide where each needed fact lives.

  1. List the facts needed: is Sam trained; the laser's rules for acrylic; is it free at 2 pm.
  2. Sam's training: stable, about one student, needed every visit, so it is saved memory, loaded at session start as a short note or database row.
  3. Acrylic rules: large, fixed, and shared by all students, so it is retrieved from the manual with search_manuals, returning only the acrylic section.
  4. Free at 2 pm: changes constantly, so it is a live tool call to check_calendar, never stored.
  5. Window at the end: instructions, tool descriptions, a short note, one manual chunk and one calendar result. Nothing else.
Your turn

A student asks: "Last time you told me my project needed a respirator mask. Can I use the spray booth now, and what is the booth's drying time for gloss paint?" The first step is done: the facts needed are (1) the earlier respirator advice, (2) whether the booth is free now, (3) the drying time. Place each fact as saved memory, retrieval or a live tool call, and say what you would do about fact (1) if the assistant had no notes.

Show a solution

(1) The earlier advice is specific to this student and stable, so it is saved memory (a note written at the last visit). With no notes, the assistant cannot know it: it should say it has no record and give the booth's current safety rules from the manual instead, rather than pretend. (2) Booth availability changes, so it is a live calendar call. (3) Drying time is fixed manual content, so it is retrieved from the booth manual.

Summary 1 min

  • The context window is everything the model sees in one call; it is limited, you pay for all of it every call, and quality can fall as it fills.
  • Between steps, your program keeps the history and re-sends it; the model keeps nothing.
  • Between sessions, nothing survives unless saved: notes or records hold small stable facts about a user.
  • Retrieval searches big fixed documents and puts only the best chunks in the window; live facts are looked up with tools.
