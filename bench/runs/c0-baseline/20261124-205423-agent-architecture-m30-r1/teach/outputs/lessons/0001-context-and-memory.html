Context and memory in an agent

By the end of this lesson you can decide, for any piece of information in the makerspace assistant, whether it belongs in the context window, in saved notes, or in a searchable manual, and say why.

Objective O3: context window, what is kept between steps and sessions, retrieval and notes as memory About 30 minutes
Why this matters for you

Your assistant must answer from long machine manuals and remember each student's training status between visits. Both jobs are memory decisions, and each one costs money, because the model is paid for by the amount of text it reads. At your design review, "what does it keep, and where?" will be one of the first questions.

Warm-up 2 min

Recall

From the agent loop: when the model wants to check the booking calendar, what does the model output, and who actually runs the calendar lookup? Answer in your head or on paper first.

Check your answer

The model outputs a request to use the tool, with the arguments (for example the machine and the date). The program around the model runs the lookup and sends the result back as new text. Keep this in mind: it means every step is a separate model call, and the program decides what text goes into each call. Today's lesson is about that text.

The context window 6 min

Start with a concrete case. A student asks your assistant: "Is the laser cutter free tomorrow at 3 pm, and do I need training?" Here is what the program sends to the model on the first call:

  • the system prompt: your instructions ("You are the makerspace assistant. Be brief. Never book without confirming.");
  • the descriptions of the tools the model may use;
  • the student's question.

The model replies with a request: check_calendar("laser cutter", "tomorrow"). The program runs it. Now, on the second call, the program sends everything above, plus the model's request, plus the calendar result. After the next tool, the third call carries all of that again, plus one more request and one more result.

Everything sent in one call is the context: the text the model can see when it writes its next output. The context window is the limit on how much text a single call can hold. Text is counted in tokens, small pieces of words, roughly three quarters of a word each in English. Anthropic describes context as the set of tokens included when sampling from a model, and context engineering as curating that set well (Anthropic: Effective context engineering for AI agents).

Two consequences matter for your budget and your design:

  1. Cost grows with length. Model usage is billed by the tokens read and written. Because each call re-reads the whole stack, a long run costs far more than the sum of the new text. Long tool results are the usual culprit: one 3,000-token manual page is paid for again at every later step.
  2. More text is not better. Anthropic notes that as the number of tokens in the context grows, the model's ability to recall information from it decreases. They call this context rot, and describe context as a finite resource, with an "attention budget" that every new token uses up (same article). Their goal is the smallest set of high-signal tokens that gets the job done.
Think of a desk. The context window is the desk's surface: only what is on it can be used right now, a crowded desk slows you down, and you pay rent per square foot every minute it is occupied. Everything else is in the filing cabinet, which is where the rest of this lesson goes.

Show the answer

The third option. Each call carries the whole stack so far, so call 6 pays for the system prompt, the question and all five earlier request and result pairs, not only the newest result.

What is kept between steps 4 min

Between steps of one run, the model keeps nothing. It is a function: text in, text out. What is "kept" is a list the program holds, usually called the message history. After each step the program appends the new request and result to that list, and sends the whole list on the next call. That is Figure 1.

This is why the loop works at all: at step 3 the model can "remember" the calendar result only because the program pasted it back in. It also means the program owns a decision the model cannot make for itself: what to include in the next call.

A common mix-up

"The model remembers what happened earlier, like a person." It is tempting because chat apps feel continuous. But the model has no stored state between calls. If the program dropped the calendar result from the next call, the model would not know the calendar was ever checked, and might check again. Memory in an agent is a property of the program around the model.

Check yourself

At step 4 the assistant asks the student, "Which day did you mean?" The student replies "Friday." What must the program do for the model to understand "Friday" on step 5?

Show the answer

The third option. The program appends the assistant's question and the student's reply to the message history and sends the full history on the next call.

Keeping the context small 4 min

If the program decides what goes in, it can also decide what comes out. Anthropic's article names three techniques for long runs (source):

TechniqueWhat it doesMakerspace example
Clearing old tool resultsOnce a result is far back in the history, remove its raw text. The article calls this one of the safest, lightest forms of compaction.Keep "calendar: laser cutter free 3 pm" but drop the full week of booking entries.
CompactionNear the limit, have the model summarize the conversation, then start a fresh window with the summary.A long booking chat becomes: "Student wants laser cutter, Friday 3 pm, has passed training, awaiting confirmation."
Sub-agentsA helper works in its own clean window and returns only a short summary to the main agent.A helper reads three manuals and returns two sentences. (Lesson on multi-agent systems comes later.)

Every one of these trades detail for space. Compaction can drop something that turns out to matter, which is why the article advises tuning a summary for recall first, then trimming. For a short makerspace question, you will likely need none of them: the simplest thing that works is a short run with short tool results.

What is kept between sessions: notes 6 min

A session is one conversation or task, from the first message to the end. When it ends, the message history is gone, because it lived in the program's memory for that run. Tomorrow's session starts with an empty stack: the system prompt, the tools, and the new question. The assistant has no idea that Priya passed laser-cutter training last Tuesday.

The fix is plain: write it down somewhere that outlasts the session, and read it back at the start of the next one. This is what Anthropic calls structured note-taking, or agentic memory: the agent regularly writes notes to storage outside the context window, and pulls them back in later. Their examples are a to-do list or a NOTES.md file; in a Pokémon-playing demo, the agent kept running tallies and objectives across context resets (source).

Anthropic's memory tool makes this concrete. The model asks to view, create, edit or delete files under a /memories folder, and your application carries out each request, just like any other tool. The memory lives entirely in your app's storage, and the tool is told to check that folder before starting a task (Memory tool docs). In other words, "memory" here is the tool loop you already know, pointed at a file store.

Good notes are small and specific. Two rules from the cost side: read only what the session needs (Priya's record, not every student's), and save facts, not transcripts. A saved line like priya: laser_cutter=passed 2026-11-17 costs a few tokens each visit. A saved chat log would cost thousands.

Your app owns the safety of this store. The docs say the handler must keep file paths inside the memory folder and recommend limiting file sizes and removing stale entries. For student records, also ask what you should not store at all, and check with your sponsor.
Check yourself

The third option. Only storage outside the context window survives a session ending; a larger window or more thinking time cannot recover text that was never saved.

Retrieval: finding the right page 6 min

The second memory problem is not "what happened," but "what does the manual say?" A laser-cutter manual may run to hundreds of pages. Putting all of it into every call would be slow, expensive and, by the context-rot point, less accurate. Instead the assistant retrieves: it finds the few relevant passages and puts only those into the context.

The standard recipe: split each manual into chunks (a few paragraphs each), and make an index so a question can be matched to chunks. Two common ways to match:

  • Keyword search, such as BM25, which scores chunks by how well their words match the question. Good for exact terms like an error code "E-27" or "air assist".
  • Embedding search, which turns text into lists of numbers so that chunks with similar meaning land close together. Good when the student's words differ from the manual's ("the cut isn't going all the way through" vs "insufficient power for material thickness").

Anthropic reports that a chunk alone can lose its context ("the revenue grew 3%" does not say which company or year), so adding a short explanation of where the chunk comes from before indexing reduced failed retrievals, and combining embeddings with keyword search did better still (Anthropic: Contextual Retrieval). For a manual, the equivalent is labelling each chunk "Laser cutter manual, Section 4: Cutting acrylic."

Two ways to wire retrieval into the loop

Up frontJust in time
HowThe program searches the manuals with the student's question and puts the top chunks in the first call.The model gets a search_manuals tool and decides when, and with what query, to search.

Anthropic describes this same split: many apps retrieve up front, while agents increasingly keep light references and load data at runtime through tools, and their coding agent uses a mix. Their advice for starting: do the simplest thing that works (source). Since your assistant already has tools and a loop, search_manuals as a tool is the natural fit.

A common mix-up

"Retrieval means the model reads the whole manual and finds the page." It is tempting because it sounds like how a person looks something up. In fact the search happens in your program, over an index, before the model sees anything. The model sees only the handful of chunks that came back. If the right chunk was not returned, the model cannot use it, which is why retrieval quality is a design question for you, not for the model.

Worked example and practice 5 min

Worked example

Place this item: "The laser cutter's maximum cutting thickness for acrylic is 6 mm," which is on page 43 of a 200-page manual.

  1. Ask: is it needed on every call? No. Most questions are about booking or training, so putting it in the system prompt would charge every call for it.
  2. Ask: does it change per student or session? No. It belongs to the machine, so it is not a note about a person.
  3. Ask: is it a long document the model can fetch? Yes. It lives in the manual index, and search_manuals brings it into context only when a question needs it.

Placement: retrieval, loaded into the context only when asked.

Your turn

Place these three items using the same questions. Step 1 is done for you: none is needed on every call, except possibly the first.

  1. "Never confirm a booking until the student says yes."
  2. "Marcus has completed the 3D printer training but not the CNC router training."
  3. The full list of 40 bookings returned by check_calendar for the whole week, when the student only asked about 3 pm tomorrow.
Show a solution

1. This rule applies to every call, so it belongs in the system prompt, which is always in context. It is short, so the cost is small.

2. This is per student and must outlast the session: saved notes, read at the start of Marcus's next session (only his record).

3. This is a tool result that was needed once. Keep the one relevant line ("free at 3 pm") in context and clear the rest, or ask the tool for a narrower date range so it never arrives. Nothing should be saved.

Summary 2 min

  • The context is everything sent to the model in one call; the window is its size limit. Every call re-sends the whole history, so cost grows, and accuracy can drop (context rot).
  • Between steps, the program keeps the history and decides what to send; the model keeps nothing. Clearing results, compaction and sub-agents trim it.
  • Between sessions, nothing survives unless the program writes it to storage (notes) and reads it back next time.
  • For long documents, retrieve: search an index in the program, and put only the best chunks in context, up front or through a tool.

Say it in your own words: without looking, explain to a teammate where Priya's training status is kept, how it gets to the model on Friday, and why the whole laser-cutter manual is not in every call.
