Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the context, in a saved note, or in a searchable manual store, and say why.

Why this matters for you

Your assistant must answer from long machine manuals and remember each student's training status between visits, all on a small budget. Those are three separate memory problems, and each has a different tool. By the end you can defend your choice for each one at the design review.

What the model sees: the context window 6 min

Start with a concrete case. A student types: "How do I change the blade on the band saw?" Before the model writes a single word, the program builds one long piece of text and hands it over. It holds:

  • the system prompt: your standing instructions ("You are the makerspace assistant. Be brief. Never book a machine without confirming training.");
  • the tool descriptions: the name, purpose and parameters of each tool;
  • the conversation so far: the student's messages, the model's earlier replies, and every tool request and result.

All of that is the context: the text the model reads in one call. The context window is the maximum amount of text the model can take in one call. Both are measured in tokens, small chunks of text, roughly three-quarters of an English word each. The window limits input and output together, and (as you will see) tokens are also what you are billed for.

The key fact is this: the model has no memory of its own between calls. Each call starts from nothing except the text the program sends. If something is not in the context, then for that call it does not exist. Anthropic's engineering team describes context engineering as curating what goes into the model at each inference step, and says this happens each time you decide what to pass to the model (Effective context engineering for AI agents).

A common mix-up

"The model remembers what we talked about earlier." It feels true because chat apps show the whole conversation. But the app is re-sending that conversation each time. Delete the history from the next call and the model has no trace of it. Memory is something your program builds; the model does not supply it.

Between steps: the context grows, and you pay for it 7 min

Inside one request, what is kept from step to step? Everything you append. Each loop iteration adds the model's tool request and the tool's result to the context, so the context only grows. That has two costs.

Cost in money. Because the whole context is re-sent on every call, you pay for the same early text again and again. Total input is the sum of the context size at each call, not the final size.

Cost in quality. A bigger context is not simply a better one. Anthropic describes context rot: as the number of tokens in the window grows, the model's ability to recall information from it decreases, because every token draws on a limited attention budget. Their advice is to find the smallest possible set of high-signal tokens that gets the job done (Anthropic Engineering).

What the program can do about it

Three ordinary tactics, all done by your code, not the model:

  • Clear stale tool results. After the model has used a 3,000-token manual page, you can replace it with a one-line stub. Anthropic calls clearing tool results one of the safest, lightest-touch forms of compaction.
  • Compact. When the conversation nears the limit, ask the model to summarise it and start a fresh context from that summary. Anthropic's advice: first maximise recall (keep everything that might matter), then trim for precision.
  • Hand off to a sub-agent. A helper explores in its own context and returns only a short summary, often 1,000 to 2,000 tokens. (Lesson on multi-agent systems comes later.)

The source for these three is the same article: Effective context engineering for AI agents.

A common mix-up

"Just buy a bigger context window and stop worrying." Current windows are large (the Claude documentation lists up to 1 million tokens for some models, see Context windows). It is tempting because it removes a hard limit. But a larger window does nothing for the bill, which still adds up every call, and it does not stop context rot. Window size sets the ceiling; it does not tell you what belongs inside.

Between sessions: notes as memory 6 min

A session is one run of the assistant: one conversation, start to finish. When it ends, the context is thrown away. If Dana finishes her laser-cutter training on Monday and returns Thursday, a new session starts with an empty context. Nothing carries over by itself.

So anything that must survive has to be written somewhere outside the context, then read back in. This is the whole idea of agent memory: write it down, and load it when it is relevant. Anthropic calls one form structured note-taking: the agent writes notes to storage outside the context window, such as a NOTES.md file or a to-do list, and pulls them back in later (Anthropic Engineering).

A concrete design for your assistant

Keep one small file per student, say students/dana.json:

{
  "trained_on": ["laser cutter", "3D printer"],
  "training_date": {"laser cutter": "2026-10-19"},
  "notes": "Prefers mornings. Booking: laser cutter, Fri 10:00."
}

Two tools handle it: read_student_record(name) and update_student_record(name, changes). At the start of a session the assistant reads the record; at the end of a task it updates it. Dana's Thursday session now knows what she completed on Monday. The model still has no memory, but the program put the notes in front of it.

Claude's own platform has this pattern built in as a memory tool: the model asks to view, create, edit or delete files under a /memories directory, and your application carries out those requests, storing them wherever you like (files, a database). The docs stress that you must reject any path that escapes /memories (Memory tool). It is the same loop you already know: the model requests, the program acts.

Don't save whole transcripts: they cost tokens to reload and mostly hold noise. Also treat personal data with care; saving a student's records is a privacy decision, not just a technical one.

Finding the right page: retrieval 7 min

The manuals are too big to paste into every call. Do the sums: a 400-page manual is on the order of 200,000 tokens, and re-sending it on three calls costs 600,000 input tokens for one question. The fix is retrieval: keep the manual in a store, find the few passages that matter for this question, and put only those in the context.

How retrieval works

  1. Chunk. Split each manual into pieces, typically no more than a few hundred tokens.
  2. Index. Build a way to search the chunks. There are two common ways, below.
  3. Search. When a student asks, search the index and take the top few chunks.
  4. Answer. Put those chunks in the context and let the model write the answer from them.

In an agent, step 3 is simply a tool: search_manuals(query). The model decides when to call it and with what words, and the result comes back like any tool result. Anthropic calls this just-in-time retrieval: keep lightweight pointers and load content through tools only when needed, rather than loading everything up front (Anthropic Engineering).

Two ways to search, and why you may want both

  • Embedding search turns each chunk and the question into lists of numbers that capture meaning, and finds the nearest. It matches by meaning: "swap the cutting blade" can find "blade replacement procedure".
  • Keyword search (the common algorithm is called BM25) matches the exact words. Anthropic notes it is particularly effective for queries with unique identifiers or technical terms, which embeddings can miss (Contextual Retrieval).

Manuals are full of exact strings: part numbers, error codes, settings. So combining both is sensible.

Where retrieval goes wrong

Cutting a manual into chunks can strip out context. Anthropic's example: a chunk reading "The company's revenue grew by 3%" no longer says which company. For you, a chunk saying "Set the speed to 40%" no longer says which machine. Their fix, contextual retrieval, prepends a short, 50 to 100 token description of where the chunk came from before indexing it. They report this cut the top-20 retrieval failure rate by 35% with embeddings, 49% when combined with keyword search, and 67% with a reranking step, in their own tests (Contextual Retrieval). A cheap version for you: put the machine name and section title at the top of every chunk.

The same article notes that a knowledge base under about 200,000 tokens (roughly 500 pages) can simply be put in the prompt without retrieval. Check your total manual size before building anything.

A common mix-up

"Retrieval means the model looks things up on its own." The model only asks. Your program runs the search, picks the chunks and decides how many go back. If the search returns the wrong chunk, the model will happily answer from it. Most "the assistant got it wrong" bugs in manual-answering systems are retrieval bugs, so test the search separately from the model.

Worked example and practice 8 min

Worked example

Request: "Can I use the band saw tomorrow, and how do I change the blade?" The system prompt plus tool descriptions plus question take 1,850 tokens. The model first calls search_manuals, which returns a 3,000-token chunk. It then calls check_calendar, which returns 200 tokens. Then it writes the answer. Ignore the model's own short requests. How many input tokens are processed in total?

  1. Count the model calls. Two tool requests plus the final answer: 3 calls.
  2. Call 1 sees the fixed part only: 1,850 tokens.
  3. Call 2 sees the fixed part plus the manual chunk: 1,850 + 3,000 = 4,850.
  4. Call 3 sees everything so far plus the calendar result: 4,850 + 200 = 5,050.
  5. Add the inputs: 1,850 + 4,850 + 5,050 = 11,750 tokens.
  6. Notice: the final context holds 5,050 tokens, yet the bill covers 11,750, because the early text was paid for three times. If the manual chunk were cleared after call 2, call 3 would drop to about 2,050 tokens.
Your turn

Same pattern, different numbers. Fixed part: 2,100 tokens. The first tool (search_manuals) returns 4,000 tokens; the second (check_training_record) returns 400. Three model calls. Step 1 is done for you: call 1 sees 2,100. Work out calls 2 and 3 and the total. Then say what you would remove to cut the total most, and from which call.

Show a solution

Call 2 sees 2,100 + 4,000 = 6,100. Call 3 sees 6,100 + 400 = 6,500. Total: 2,100 + 6,100 + 6,500 = 14,700 tokens. The biggest saving is dropping or shrinking the 4,000-token result, because it is re-read on call 3 as well; clearing it before call 3 would make that call about 2,500 tokens and save about 4,000. A smaller retrieved chunk would save on both calls.

(d) Lives in the context, and is dropped when the session ends. The reasoning: match each fact's lifespan and size to the cheapest place that keeps it correct.

Summary 3 min

  • The model has no memory between calls. The program rebuilds the context each time, and that context is all the model sees.
  • Within a request the context grows with every tool result; you pay for it on every call, and quality can drop as it fills. Clear, compact or delegate.
  • Between sessions nothing survives unless it is written to a note or file and loaded back.
  • Long manuals go in a searchable store; a search tool brings only a few chunks into context. Use keyword and embedding search together for exact terms.
